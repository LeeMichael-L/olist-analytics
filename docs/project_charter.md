# Olist 数据研究项目 · 项目章程

> 版本：2026-10-12（阶段0立项时确认，阶段1期间更新了团队分工）
> 章程记录项目立项时的目标与规划。此后对口径、范围、方法的调整，以 `decision_log.md` 为准；各阶段的实际完成情况见 `stage_summaries/`。

## 1. 项目背景与目标

本项目以 Olist 内部数据研究团队的视角，回答一个主问题：**平台如何在保持交易规模增长的同时，提升买家满意度和卖家质量？哪些杠杆的投入产出最高？**

**背景。** Olist 是连接巴西中小卖家与主流电商平台的服务商，收入来自卖家的订阅费和佣金。卖家是 Olist 的直接客户；买家体验通过评分影响卖家表现，进而影响平台。因此本项目以卖家为主线，买家体验作为验证维度。

**商业目标**

- 诊断 2017 年 1 月至 2018 年 8 月的经营表现与增长来源
- 定位影响买家满意度的关键因素，量化履约问题的影响
- 建立卖家健康度评估方法，识别优质与问题卖家
- 评估各获客渠道带来的卖家质量
- 提出 3 条附带量化影响和局限性的行动建议，并为最优策略设计实验方案

**能力目标**（项目同时作为数据分析/商业分析实习的作品集）

- 覆盖五大面试高频考点：指标体系、归因分析、留存与同期群、漏斗、AB 测试
- 产出可公开展示的 GitHub 仓库、Tableau Public 看板和中英双语 README

## 2. 团队角色与分工

团队采用导师带教模式：Claude 作为团队 leader 负责规划、讲解和审查，负责人亲手完成每一步操作和分析，目标是项目结束时具备独立分析能力。

| 角色 | 承担者 | 职责 |
| --- | --- | --- |
| 团队 leader / 导师 | Claude | 拆解任务、讲解每一步的目的和方法；提出引导性问题；审查代码和结论并指出问题 |
| 分析师（学习者） | LeeMichael-L | 亲手搭建环境、运行 SQL 和 Python、解读结果、做出数据决策、撰写结论和阶段总结；对每一行代码能讲清楚 |

**协作方式**

1. 每一步开始时：leader 说明目标、背景知识和完成标准
2. 分析师动手：运行代码；卡住时带着报错和尝试来问
3. 交作业：把代码和运行结果发回，leader 审查、提问、指出改进点
4. 修改直到通过，再进入下一步
5. 阶段结束：撰写阶段总结，审阅后归档
6. 任何改变口径、范围或结论方向的决定，都由分析师提出理由、记入决策日志

**分工细则（2026-10-12 调整）：** 基础设施代码（建表、导入、清洗、环境配置）由 leader 提供，分析师读懂并运行；**回答业务问题的关键查询**由 leader 给出思路和提示，分析师自己写代码。每个关键分析都配图表，图表类型由分析师根据问题类型选择并说明理由。

**原则：** 慢就是快。宁可一步多花一天弄懂，也不跳过不理解的地方。面试时被追问的是分析师本人，判断标准是能否独立讲清楚每一步为什么这样做。

## 3. 研究框架与范围

研究按 L0 到 L4 五层递进，数据质量、口径验证和统计严谨性贯穿全程。北极星指标为**已送达订单的商品交易额**（`order_items.price` 之和，不含运费，不等于 Olist 收入），护栏指标为平均评分、活跃卖家数和按时送达率。

| 层级 | 模块 | 核心问题 | 优先级 |
| --- | --- | --- | --- |
| L0 | 商业模式与指标口径 | 北极星指标、护栏指标和各指标口径如何定义？ | P0 |
| L1 What | 1 指标体系与趋势 | 经营现状如何？增长来自哪里？ | P0 |
| L1 What | 2 交易额波动归因 | 某月的波动由哪些因子、哪些维度造成？（LMDI 对数分解） | P1 |
| L2 Why | 3 履约与满意度 | 卖家发货和物流运输两个环节，分别对评分有多大影响？ | P0 |
| L2 Why | 4 商品与品类经营质量 | 哪些品类值得支持，哪些在损害体验？ | P1 |
| L3 Who | 5 买家复购与价值 | 复购率多高？增长靠新客还是老客？ | P0 仅复购率；P1 完整同期群 |
| L3 Who | 6 卖家分层与健康度 | 哪些卖家创造价值，哪些拖累口碑？ | P0 |
| L3 Who | 7 卖家获取漏斗与渠道质量 | 哪些渠道带来的卖家签约后表现最好？ | P0 |
| L4 How | 8 策略测算与实验设计 | 候选策略的静态测算结果如何？如何用实验验证？ | P2 |

**数据范围**

- Olist 巴西电商公开数据集（9 张表，约 10 万订单）
- Olist 营销漏斗数据集（线索表、签约表，8,000 条线索，通过 `seller_id` 关联）
- 分析窗口：2017-01 至 2018-08（D-016）

**不做什么**

- 不分析利润：没有成本和佣金明细
- 不把静态测算当作因果效果：策略的真实效果只能通过实验验证
- 不编造实验数据：模块 8 只做实验设计方案
- 不引入 Docker、Airflow、dbt 等重工程工具

## 4. 阶段计划与里程碑

项目分 6 个阶段；阶段 2 结束即可把项目写进简历开始投递。每个阶段须通过验收标准、完成阶段总结后，才进入下一阶段。

| 阶段 | 内容 | 交付物 | 验收标准 |
| --- | --- | --- | --- |
| 0 立项 | 确定目标、框架、规范 | 本项目章程 | 负责人确认章程 |
| 1 数据准备与质量审计 | 建库、导入、ODS/DWD 分层、数据质量检查 | 建表与导入脚本、数据质量审计脚本、数据字典、ER 图 | 各表行数与源文件一致；已知数据陷阱全部有检查结果和处理决定 |
| 2 P0 分析 | 模块 1、5（复购率）、3、6、7 | 各模块 SQL 与结论、中文 README 初版 | 每个模块有结论、数字和局限性说明 |
| 3 P1 分析 | 模块 2、4、5（完整同期群） | 各模块 SQL 与结论、索引优化记录 | 同上；EXPLAIN 优化前后对比有实测耗时 |
| 4 P2 分析 | 模块 8 | 情景测算、AB 实验设计方案 | 测算标注为上限估计；样本量计算可复现 |
| 5 交付 | 看板、报告、文档 | Tableau Public 看板、一页结论报告、中英 README | 外部读者能在 5 分钟内看懂主问题、结论和建议 |

## 5. 工作规范

**技术栈**

| 用途 | 工具 |
| --- | --- |
| 数据库与分析 | MySQL 26.7，脚本兼容 MySQL 8.0 及以上（D-009） |
| 统计建模 | Python：pandas、scipy、statsmodels |
| 可视化 | Tableau Public |
| 版本管理 | Git + GitHub |

**数据分层**

| 层 | 目录 | 作用 |
| --- | --- | --- |
| ODS 原始数据层 | `sql/01_ods/` | 原样落地，不清洗、不设业务主键 |
| DWD 明细数据层 | `sql/02_dwd/` | 清洗、关联、打标记；只打标记不删数据；设主键 |
| DWS 汇总层 | `sql/03_dws/` | 按主题汇总的宽表 |
| ADS 应用层 | `sql/04_ads/` | 各分析模块的结果表 |

**命名规范**

- 表名：`层级_主题`，如 `dwd_order_items`、`dws_seller_monthly`
- 标记字段：以 `is_` 或 `has_` 开头，取值 1 / 0
- 字段：小写加下划线

**SQL 编码规范**

- 关键字大写，每个子句换行，复杂逻辑用 CTE 拆分
- 每个文件开头注明：阶段、目的、输入、输出、作者、日期
- 每个 CTE 上方用一行注释说明它在做什么
- 计算比率时显式处理分母为 0 的情况（`NULLIF`）
- 每个脚本末尾附核对查询，并与已知数字对照

**Git 规范**

- 每完成一个可运行的步骤就提交一次
- 提交信息格式：`[阶段] 做了什么`，如 `[S1] 新增DWD层清洗脚本`
- 提交前先看 `git status`，与预期对比
- 每个阶段结束打一个标签，如 `stage-1-done`
